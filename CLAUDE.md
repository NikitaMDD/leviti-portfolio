# CLAUDE.md

Инструкции для Claude Code при работе в этом репозитории.

## О проекте

Портфолио-сайт для диджея. Задача сайта — представить артиста: кто он, что играет,
где выступал, дать возможность послушать миксы и связаться по вопросам букинга.

Сайт публичный, без личного кабинета и авторизации. Контент обновляется нечасто
(новые миксы, новые ивенты, фото) — это статический контентный сайт, не веб-приложение.

Проект сейчас на самом старте: кода ещё нет, есть только описание концепции в
[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md). При скаффолдинге и дальнейшей разработке
опирайся на принципы ниже.

## Дизайн-принципы

Приоритет — ясность и контент, а не экспериментальная механика взаимодействия.

- Простая, понятная навигация — посетитель сразу понимает, что это за сайт и что тут делать
- Контент на первом плане: фото, миксы, контакты
- Минимум когнитивной нагрузки — никаких загадочных интерфейсов, скролл-триггеров ради эффекта и т.п.

Явный антипример — [narrowdesign.com](https://www.narrowdesign.com): сильный дизайн сам
по себе, но слишком концептуальный и непонятный для формата портфолио. Не ориентироваться
на такой подход при вёрстке UI.

Единственное место, где дизайну намеренно даётся больше свободы — hero-секция с
WebGL-эффектом (см. ниже); остальной сайт остаётся дисциплинированным и спокойным.

## Hero-эффект (ключевая фича)

Анимированный WebGL-фон на главной странице — органичные шумовые/flow-волны (в духе
mesh gradient/simplex noise), тёмный фон с оранжево-красно-бирюзовыми цветами (палитра
выше). В покое — медленный темп. При воспроизведении self-hosted трека — реагирует в
реальном времени на звук через Web Audio API (`AnalyserNode`), модулируя параметры
шейдера (скорость/интенсивность) под амплитуду/частоты. Для embed-треков остаётся в
спокойном режиме (доступа к аудиопотоку iframe нет из-за CORS).

Кандидат-библиотека: `@paper-design/shaders-react` (или vanilla `@paper-design/shaders`) —
готовые WebGL-шейдеры (mesh gradient, simplex noise, warp и др.), не требует написания
GLSL с нуля, пропсами настраиваются цвета/скорость/дисторшн. Компонент — island
(`client:load` или `client:visible`), не влияет на SSG остальной части сайта.

## Технический стек

- **Astro** (SSG) — выбран сознательно вместо Next.js: для контентного сайта без личного
  кабинета SSR избыточен, а Astro отдаёт минимум JS на клиент (islands architecture), что
  даёт быструю загрузку и хороший SEO из коробки
- Интерактивные блоки (плеер миксов, WebGL hero-эффект) — точечно, как island-компонент
  (React/Vue/Svelte), только там, где статикой не обойтись
- Хостинг: GitHub Pages + GitHub Actions (автодеплой), арендованный домен

При выборе решений держаться Astro-идиом: минимизировать client-side JS, гидратировать
компоненты только там, где реально нужна интерактивность (`client:idle` / `client:visible`
предпочтительнее `client:load`, кроме hero-эффекта, который виден сразу при загрузке).

Почему не другие варианты (кратко):
- **Vanilla HTML/CSS/JS** — минимум обучения нового, неудобно обновлять контент
- **Next.js с SSR** — избыточная сложность (нужен постоянно работающий сервер) для сайта,
  где контент почти статичен и нет персонализации под юзера
- **SvelteKit / Nuxt** — рассматривались как альтернативы, тоже валидны, но Astro проще
  стартовать и лучше заточен именно под контентные сайты

## Ивенты: как заполнять `src/content/events.yaml`

Секция «Ивенты» на главной (`src/components/EventsSection.astro`) целиком строится из
одного файла `src/content/events.yaml`, схема полей — в `src/content.config.ts`.
Вёрстку при добавлении ивента трогать не нужно.

Файл — YAML-список, каждый ивент начинается с `- ` и имеет такие поля:

| Поле | Обязательно | Что писать |
|---|---|---|
| `id` | да | уникальный слаг латиницей, например `gadalnya-2026-10` (повтор `id` — ошибка сборки) |
| `date` | да | дата начала вечера `ГГГГ-ММ-ДД`. Ночь с 26 на 27 — это `26` |
| `title` | да | название вечеринки или площадки — то, что крупно в строке |
| `venue` | нет | площадка, если в `title` название вечеринки (мелко под названием) |
| `city` | да | `Москва`, `Санкт-Петербург`, `Тула` — показываются кодами МСК/СПБ/ТУЛ. Другой город выведется как есть (код можно добавить в `CITY_CODES` в `src/lib/cities.ts`) |
| `role` | нет | одно из: `headline`, `b2b`, `warm-up`, `closing`, `showcase`, `resident`. Любое другое значение — ошибка сборки |
| `tickets` | нет | полная ссылка `https://…` на билеты. Есть ссылка — есть кнопка «Билеты» |
| `post` | нет | полная ссылка `https://…` на пост/рилс. Есть ссылка — есть кнопка «Пост» |
| `tbc` | нет | `true`, пока название/дата не уточнены: вместо даты `--.--` и метка «уточняется». Когда данные точные — строку удалить |

Пример полностью заполненного ивента:

```yaml
- id: garage-night-2026-11
  date: 2026-11-14
  title: Garage Night
  venue: Гадальня
  city: Тула
  role: headline
  tickets: https://example.com/tickets
  post: https://www.instagram.com/p/XXXX/
```

Правила и подводные камни:

- Отступы — два пробела, табы YAML не принимает. Поля одного ивента выровнены по `id`
- Порядок записей в файле не важен — сортировка по дате делается сама
- «Скоро» / «Прошедшие» делятся по дате на момент сборки по московскому времени
  (ивент в день выступления ещё в «Скоро»). Сайт пересобирается раз в сутки по крону
  в `.github/workflows/deploy.yml`, так что прошедший ивент сам уедет вниз
- Если в `title` есть двоеточие или кавычки — взять значение в кавычки: `title: "Party: Vol. 2"`
- Прошедших показывается максимум 6 самых свежих (`PAST_LIMIT` в компоненте), на
  невысоких экранах — 4: страница листается по экранам, внутреннего скролла у секции нет.
  Старые записи удалять не нужно, они просто не выводятся
- Нет ни одного будущего ивента — в «Скоро» автоматически показывается приглашение на букинг
- Проверка: `npm run build` — ошибка в поле (неизвестная `role`, битая ссылка, нет
  обязательного поля) падает с указанием записи. При добавлении/переименовании самого
  `content.config.ts` запущенный `npm run dev` нужно перезапустить — новую коллекцию
  он не подхватывает; правки в `events.yaml` подхватываются на лету

## Букинг: контакты и отправка формы

Секция `src/components/BookingSection.astro`. Контакты и ключ формы — в одном файле
`src/lib/contacts.ts`:

- `telegram`, `instagram` — ник без `@`; `telegramChannel` — полная ссылка на канал
  или `null` (тогда пункт не выводится)
- `WEB3FORMS_KEY` — заявки уходят на почту через [Web3Forms](https://web3forms.com):
  ввести там почту Оли → access key придёт письмом → вставить в `WEB3FORMS_KEY`.
  Ключ публичный по задумке сервиса, в секреты GitHub его класть не нужно.
  Пока ключ пустой, форма ничего не отправляет и предлагает написать в Telegram
- Поля формы: дата, город, формат (Клуб/Бар/Частное/Корпоратив/Фестиваль — список
  `FORMATS` в компоненте), площадка, имя, контакт, детали. В письме тема
  `Букинг: дата · город · формат`. Дата — текстовое поле с маской `ДД.ММ.ГГГГ`
  (точки подставляются сами, несуществующая или прошедшая дата не пройдёт проверку),
  в имени цифры не вводятся
- После успешной отправки форма заменяется экраном «Заявка у меня»: контакт
  организатора, его строка афиши и кнопка «Отправить ещё одну» (очищает форму).
  Ошибка отправки — строка под кнопкой с предложением написать в Telegram
- Под формой — черновик строки афиши, собирается из полей на лету в вёрстке строк
  секции «Ивенты»; при изменении вида строк ивентов — поправить и его
- На мобильном форма скроллится внутри секции (`data-inner-scroll` +
  `data-lenis-prevent`, логика `innerScrollAllows` в `index.astro`)

## Формат работы

Артист (Оля) очень занята и вовлекается в проект точечно — не по ходу разработки,
а когда ей показывают готовый результат. Из этого следует конкретный процесс:

1. Собираем прототип (сейчас — визуальный, дизайн-система выше) и показываем ей
2. Она даёт фидбек одним заходом, иногда резко меняющим направление —
   вплоть до «переделать всё» по цвету/типографике/структуре
3. Не переинвестировать в детали и полировку до первого одобрения концепции —
   дизайн-система выше уже прошла один такой пересмотр (v1 → v2) и может смениться снова

Не считать текущую дизайн-систему и структуру контента финальными до подтверждения
от Оли — при получении фидбека сразу обновлять этот файл, а не только код.
